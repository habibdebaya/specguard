Checking aircraft requirements with Z3

A case study on the ARP4754B wheel brake system

Background

Before an aircraft is built, engineers write down what it has to do and how safe it has to be. These statements are called requirements. They start with the aircraft as a whole. Then they are broken down into requirements for each system, like the brakes, and then for each part of that system.

ARP4754B, published by SAE International, is a guideline for this process. Its Appendix E walks through one full example, following a wheel brake system from aircraft-level requirements down to the brake controller. Because each level is written up in its own documents, the same requirement gets restated across safety analyses, specifications and assumption lists. Every restatement is a chance for the meaning to shift. A condition gets dropped, a unit changes from per flight to per hour, or “above” becomes “at or above.” Each version still reads fine on its own, so across hundreds of pages these shifts are easy to miss.

We built specguard to catch these shifts. It converts each requirement into a precise logical statement. After a manual review, a solver called Z3 compares the statements and finds the exact cases where two versions of a requirement disagree. We ran it on 176 requirements and assumptions from Appendix E. The rest of this article explains how specguard works and walks through one of the problems it found.

This matters because every safety rule set early on has to survive into the final specification, and specguard shows exactly where one didn’t.

Method

specguard works in three steps. First, it reads a section of the standard and converts each requirement into a logical statement, keeping the requirement’s ID and original text alongside it. Second, the statements go through manual review. Third, the reviewed statements go to Z3, a logic solver that either finds values that make every statement true at once or proves that no such values exist.

The main check asks whether a later document keeps a rule from an earlier one. Call the earlier rule R and the later document S. specguard asks Z3 one question. Is there any situation where S is followed but R is broken? If the answer is no, the check passes, because following S always means following R. If the answer is yes, the check fails, and Z3 hands back the exact situation where it happens. That situation is called a counterexample. This check only runs in one direction, because the later document is allowed to add detail or be stricter as long as it doesn’t lose the earlier rule.

Some statements are meant to say exactly the same thing, like a limit copied from one table into another. For those, one direction is not enough. A pass in one direction only shows that the restatement is at least as strict as the original, and it could still be stricter. So specguard runs the check in both directions, and the two statements only mean the same thing if both pass.

Here is a small example of that double check. Say the original rule is “speed must be below 100” and a later document restates it as “speed must be at most 100.” The restatement is supposed to mean the same thing as the original, so we check it both ways.

Original (R)
speed < 100
Restatement (S)
speed ≤ 100

Does S keep R? Is there a speed where S is followed but R is broken?

speed ≤ 100 and speed ≥ 100→ yes, speed = 100FAIL

Does R keep S? Is there a speed where R is followed but S is broken?

speed < 100 and speed > 100→ noPASS

The first check fails. The restatement is looser than the original, and Z3 finds the exact speed where they split, which is 100. The second check passes, because any speed below 100 is also at most 100. Both checks have to pass for the two statements to mean the same thing, so the restatement changed the rule.

Worked Example: the brake control gap

Across the 176 requirements and assumptions, our analysis found five logical inconsistencies between documents. Here we go through one of them.

The wheel brake system has two control signals. We will call them N, which turns on the normal brake control, and A, which turns on the alternate brake control. Early in the design, the safety analysis (Table E13, p. 137) requires exactly one of the two to be on at any time. It does this with two rules. The first says that if N is on, A must be off. The second says that if N is off, A must be on.

Later, the final specification for the brake system (Table E19, p. 144) restates these requirements. It keeps the first rule but leaves out the second.

Safety analysis (Table E13)
if N is on, A must be offif N is off, A must be on
Final specification (Table E19)
if N is on, A must be off

Going through every combination of the two signals shows where the documents differ.

N A Safety analysis (Table E13) Final specification (Table E19)
onoffallowedallowed
offonallowedallowed
ononforbiddenforbidden
offoffforbiddenallowed

The last row is the problem. When both signals are off, neither brake control is on. The safety analysis forbids this, but the final specification allows it. specguard caught this with the one-way check described above. It asked Z3 whether there is any situation where everything in the final specification is followed but the second rule from the safety analysis is broken. Z3 answered yes and returned N off and A off, which is the last row of the table. So the check fails, and that state is the counterexample. If the second rule is added back into the final specification, the check passes.

Conclusion

Requirements can change slightly when they are restated, and when each document reads fine on its own, those changes are hard to spot. In the brake example, one missing rule meant the final specification allowed both brake controls to be off. specguard found it by converting the requirements into logic and letting Z3 search for a case where the two documents disagree. We think pairing automatic conversion with a solver like Z3 is an interesting direction to work on.

Everything behind this article is in the specguard repository. It has the Appendix E requirements as logical statements next to their original text, the solver that runs the checks, and the instructions specguard uses to convert a standard. You can rerun the whole analysis from the repository root with the two commands below and see the result of every check. No API key is needed.

pip install z3-solver
python solve.py

The repository also explains how to run the same checks on your own requirements.

Reference. SAE International, ARP4754B, Guidelines for Development of Civil Aircraft and Systems, December 2023, Appendix E, “Development Assurance Contiguous Example.”
